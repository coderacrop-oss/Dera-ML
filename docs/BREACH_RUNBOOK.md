## 1. ขั้นตอนตามเวลา (Timeline → Action)

| ชั่วโมง | ขั้นตอน | ผู้รับผิดชอบ |
|---|---|---|
| **H+0** | **ระบุขอบเขต breach** — ข้อมูลอะไร กี่ record กี่ partner ได้รับผลกระทบ | On-call Engineer |
| **H+1** | **Contain** — revoke API key ที่ถูก compromise (`APIKeyManager.revoke_key()`), isolate store ที่ได้รับผลกระทบ, หยุด pipeline ถ้าจำเป็น | On-call Engineer |
| **H+4** | **ประเมิน severity** — ดูตาราง Severity Assessment ด้านล่าง | Security Lead + Engineering Lead |
| **H+6** | **แจ้งทีมภายใน** — CEO, Legal, และ Data Protection Officer (ถ้ามี) | Security Lead |
| **H+24** | **แจ้ง partner** ที่ได้รับผลกระทบโดยตรง ใช้ template ในหัวข้อ 4 | Relationship Manager + Legal |
| **H+72** | **แจ้ง PDPC** (ถ้า breach มีความเสี่ยงสูงต่อสิทธิและเสรีภาพของ data subject) ใช้ template ในหัวข้อ 5 | Legal / Data Protection Officer |
| **หลัง H+72** | **แจ้ง data subject** (ตามที่ PDPC กำหนด หรือถ้า breach มีความเสี่ยงสูงมาก) | Legal + Partner |
| **Post-incident** | **Root cause analysis** + **แก้ไขระบบ** + **อัปเดต runbook** | Engineering |

> **กฎเหล็ก:** ถ้าไม่แน่ใจว่า breach ถึงเกณฑ์แจ้ง PDPC หรือไม่ — ให้แจ้งไว้ก่อน ดีกว่าพลาด deadline 72 ชั่วโมง

## 3. Severity Assessment Guide

ใช้ตารางนี้ประเมินว่า breach ต้องแจ้ง PDPC หรือ data subject หรือไม่

| ปัจจัย | ความเสี่ยงต่ำ | ความเสี่ยงกลาง | ความเสี่ยงสูง |
|---|---|---|---|
| **ประเภทข้อมูลที่รั่ว** | Hashed customer_id เท่านั้น | Hashed ID + ข้อมูลธุรกรรม (ไม่มีชื่อ/เบอร์) | Raw customer_id (เบอร์/email) หรือข้อมูลส่วนตัวอื่น |
| **จำนวน record** | < 100 | 100 – 10,000 | > 10,000 |
| **ผู้เข้าถึงข้อมูล** | ภายในองค์กร (accidental) | ภายนอก แต่ไม่ทราบว่าใช้งาน | ภายนอก + มีหลักฐานว่าเข้าถึงจริง |
| **โอกาส re-identification** | ต่ำมาก (เฉพาะ hashed ID ไม่มีข้อมูลเสริม) | กลาง (hashed ID + pattern ธุรกรรม) | สูง (raw ID หรือมีข้อมูลเสริมเพียงพอ) |

### กรณีพิเศษ: ถ้า customer_id ถูก hash ทั้งหมด

ถ้าระบบ hash customer_id ด้วย HMAC-SHA256 + per-store salt (ตาม `data_security.py`) แล้ว:

- ผู้ที่ได้ข้อมูลไปจะ **ไม่สามารถทราบ** ว่า hashed ID สอดคล้องกับลูกค้าคนไหน โดยไม่มี salt
- ความเสี่ยงต่อ data subject **ต่ำมาก** เพราะไม่สามารถ re-identify ได้โดยตรง
- อย่างไรก็ตาม ยังต้องประเมินข้อมูลอื่นที่อาจรั่วด้วย (เช่น transaction pattern)
- แนะนำ: ให้ Legal ยืนยันก่อนตัดสินใจ **ไม่** แจ้ง PDPC

## 6. Post-Incident Checklist

หลังจาก incident สงบแล้ว ต้องดำเนินการดังนี้:

- [ ] Root cause analysis เสร็จสมบูรณ์และบันทึกไว้
- [ ] แก้ไข vulnerability ที่ทำให้เกิด breach
- [ ] Rotate API keys ทั้งหมดที่เกี่ยวข้อง
- [ ] ตรวจ audit log เพื่อหา access ที่ผิดปกติช่วงก่อนหน้า
- [ ] อัปเดต runbook ถ้าขั้นตอนใดบกพร่อง
- [ ] แจ้ง partner ว่า remediation เสร็จแล้ว
- [ ] ส่ง final report ให้ PDPC (ถ้าแจ้งไปแล้ว)
- [ ] ทบทวน data retention — ลบข้อมูลที่ไม่จำเป็นออก
